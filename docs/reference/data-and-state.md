# Data and state reference

> Status: Reviewed against HEAD 800ac16 by a fresh reader.

The persistent data model has seven PostgreSQL entities. The BFF also keeps carts and read-optimized copies in process memory, while the browser stores one demo-mode preference and keeps working state in memory. ## Persistent entities

PostgreSQL is the durable source for catalog, orders, asset data, users, and sign-in sessions. The BFF owns writes through its domain services, except direct database administration through Prisma Studio, which bypasses domain events. Monetary amounts use integer minor units with a currency string. Order lines preserve product and price snapshots; they do not depend on a live product row.

| Entity      | Ownership and lifecycle                                                                                                                                             | Constraints and notable fields                                                                                                                                                                                                                                    | Usage                                                                                                           |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Product     | Catalog data is stored in PostgreSQL and loaded into a BFF cache at startup. Catalog creation writes the row and updates that process cache.                        | `productId` and `sku` are unique. Price is an integer minor amount plus currency. Inventory is absent from the current schema.                                                                                                                                    | Public catalog and product lookup; order lines retain their own product snapshot.                               |
| Order       | Checkout writes the order and nested lines. Orders remain in PostgreSQL and warm the BFF order cache at startup. Session and recipient ownership are optional.      | `orderId` is unique. Optional `clientRequestId` is unique; PostgreSQL permits multiple null values. `customerName`, `sessionId`, `ownerUsername`, and `ownerEmail` are nullable. Owner strings have no user foreign key and at most one is populated by checkout. | Order history, idempotent checkout replay, account and anonymous ownership queries, status and hot-order reads. |
| OrderLine   | Created with its order and deleted when that order is deleted. It stores the name, product identity, quantity, unit price, and line total as a historical snapshot. | Foreign key targets the order's unique public identifier and cascades on delete. Product identity is not a foreign key.                                                                                                                                           | Durable order detail and monetary calculation records.                                                          |
| AssetConfig | Geometry parameters are stored by category and loaded into an in-memory BFF cache.                                                                                  | Category is unique; parameters are JSON.                                                                                                                                                                                                                          | Visualizer procedural geometry fallback and tunable dimensions.                                                 |
| AssetModel  | Asset references are stored by category and variant. Multiple variants are allowed; the BFF selects the most recently updated primary model per category.           | Category plus variant is unique. Variant defaults to `default`, `assetFormat` to `glb`, and `isPrimary` to true. Multiple primary rows per category are permitted.                                                                                                | Visualizer baked model selection with procedural configuration fallback.                                        |
| User        | Registration creates normalized username and email values with a password hash. Users remain in PostgreSQL.                                                         | Username and email are independently unique. Passwords are stored as scrypt hashes, never plaintext.                                                                                                                                                              | Sign-in and account ownership lookup.                                                                           |
| AuthSession | Sign-in creates a database row with an expiry. Logout deletes the presented session; an expired row is deleted when its token is presented.                         | Token hash is unique; user foreign key cascades on user deletion. Expiry is stored as a timestamp.                                                                                                                                                                | Persistent validation of the browser's sign-in cookie.                                                          |

Order `status` and Product `inventory` are not current fields. Order temperature is derived from placement time and the configured cooling interval. Nullable values include customer name, idempotency key, session owner, and account recipient; older, seeded, or anonymous orders can lack those values. Order ownership matching uses normalized username or email strings, so an order can name a recipient before that account exists. Checkout limits account ownership to one recipient field, but the schema does not enforce that invariant. New checkout orders store no customer name.

## Seed data

Seeding is repeatable for rows it owns. It removes products other than the one supported catalog item, upserts that product, and creates the demo order only if it is missing. Existing demo users keep their current password hashes because user upserts do not update existing rows. Seeded account orders are also inserted only when absent, except the primary demo user's hot order has its placement time refreshed on each seed. The seed refreshes geometry configs and the default drink model on each run. It does not clear existing orders, lines, users, auth sessions, or unrelated asset rows.

The demo order contains a line for a product absent from the one-item catalog. This is valid because order lines snapshot product data and have no product foreign key. Seed records without a session owner are excluded from session order listing. Seeded recipient orders appear in global and matching account reads, and can target an unregistered email.

## BFF memory and derived state

Each BFF process maintains its own cart map, catalog cache, order cache, order indexes, and asset caches. Restarting a process clears cart state and rebuilds the durable-data caches from PostgreSQL. These caches do not form shared state across replicas.

| State                     | Lifetime and refresh behavior                                                                                                                                                                                                                 | Usage                                                                                                                                                      |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cart map                  | One cart per session cookie in process memory. A selected cup reserves the cart for one hour. Expiry clears contents lazily during access; no timer or background sweep runs, and empty entries remain in the map. Checkout resets the entry. | Cart reads, reservation enforcement, and checkout. A BFF restart loses carts even if the browser keeps its session cookie.                                 |
| Catalog cache             | Loaded from PostgreSQL at startup. Successful catalog creation appends to the local cache. Direct database edits do not refresh it automatically.                                                                                             | Synchronous catalog and product reads.                                                                                                                     |
| Order cache               | Loaded with lines at startup. New orders append to it. Separate in-memory indexes support global idempotency replay and session ownership. A database uniqueness-race winner can also enter the cache.                                        | Global, single-order, and session order reads and checkout replay. Account history, single-order status, and account hot status query PostgreSQL directly. |
| Asset caches              | Config and primary model maps load at startup. An explicit refresh replaces each map from database state.                                                                                                                                     | Synchronous visualizer reads. Direct database edits remain invisible until refresh or process restart.                                                     |
| Derived order temperature | Calculated from `placedAt` at read time using the configured cool-down. It is not persisted.                                                                                                                                                  | Order views and status responses.                                                                                                                          |

Catalog creation, cart addition, order creation, and successful checkout emit domain events for visualization consumers. Expiry clears cart contents during access without emitting an event; asset refresh also emits no event. Prisma Studio writes directly to PostgreSQL and emits no domain event; a running process can retain stale caches after such edits. Cart `updatedAt` is a fixed placeholder, while a separate internal epoch tracks cart changes.

The anonymous `sid` cookie identifies a cart and session-owned orders. The `auth` cookie identifies a sign-in session independently, so login and logout do not change the cart. The raw auth token exists in the HTTP-only cookie; PostgreSQL stores only its SHA-256 hash. Expired auth rows are removed when presented, while no periodic session cleanup runs. Signing in again creates another row without deleting older sessions. Session lifetime is defined in the [configuration reference](configuration.md#bff).

## Browser state

The browser keeps the BFF cookies and one persistent demo-mode override. Cookie attributes, minting, and clearing follow the [HTTP API reference](http-api.md#shared-http-behavior).

Setting `expresso_demo_mode` to exactly `true` in local storage turns demo mode on; removing it returns control to the build-time setting. The demo cart is a module-level in-memory value and has no reservation expiry. In normal mode, the browser fetches the session cart from the BFF and SWR caches fetched state in browser memory. Component state includes drawer visibility, form selections, filters, quick views, and loading or error indicators. No browser database or session-storage cart is defined.

## Performance outputs and storage

Local performance runs write scenario HTML and JSON summaries, selected run logs, and generated datasets under the performance test tree. Compose bind mounts expose reports and data to the host; repeated scenario names can replace matching files. The performance cleanup command removes reports and logs while preserving the reports placeholder. Dataset removal is separate: after execution, the CLI can prompt to delete consumed dataset files. Existing reports or datasets may predate a run; the matching execution result and log establish the run result.

| Storage                                  | Persistence boundary                                                                                                                              | Retention behavior                                                                                                                                | Usage                                                     |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Main Compose PostgreSQL volume           | Named Docker volume mounted at PostgreSQL's data directory.                                                                                       | Persists across container restarts; removal of the volume removes its database contents. No database row-retention policy is configured here.     | Local application data.                                   |
| Compose tracing and dashboard volumes    | Named volumes hold Tempo, Prometheus, and Grafana state.                                                                                          | Prometheus keeps six hours of time series. Tempo keeps blocks for 24 hours. No Grafana retention limit is configured.                             | Local observability state.                                |
| Compose performance reports and data     | Host directories are bind-mounted into k6 containers.                                                                                             | Files persist until replaced or removed. Report cleanup does not remove datasets; consumed datasets have a separate confirmation prompt.          | Scenario outputs and datasets shared between runs.        |
| Kubernetes PostgreSQL PVC                | A 1 GiB ReadWriteOnce claim backs the single-replica database.                                                                                    | Survives pod restarts; the manifest identifies minikube profile deletion as its removal boundary. No database row-retention policy is configured. | Cluster application data.                                 |
| Kubernetes artifact PVC and object store | A 2 GiB ReadWriteOnce claim backs the local SeaweedFS S3-compatible store. Workflow artifacts use the `punch-artifacts` bucket with per-run keys. | The manifests define no object expiry or pruning policy.                                                                                          | Workflow datasets and run artifacts in the local cluster. |
