# Build and deploy reference

> Status: Reviewed against HEAD 800ac16 by a fresh reader.

Workspace builds produce application outputs, and container builds produce runnable images. Kubernetes uses locally tagged images built into minikube or pushed to its registry; Vercel builds only the web application. CI defines ten jobs, including two stub jobs and a build job that invokes some placeholder package scripts.

Drift anchors: `package.json`, `pnpm-workspace.yaml`, `turbo.json`, `apps/bff/package.json`, `apps/web/package.json`, `packages/*/package.json`, `tests/*/package.json`, `tests/performance/k6/package.json`, `apps/bff/Dockerfile`, `apps/web/Dockerfile`, `apps/visualizer-3d/Dockerfile`, `infra/docker/k6.Dockerfile`, `infra/docker/k6-browser.Dockerfile`, `infra/docker/compose.yaml`, `infra/docker/compose.dev.yaml`, `infra/docker/compose.performance.yaml`, `.github/workflows/ci.yml`, `infra/k8s/`, `infra/k8s/perf/`, `infra/argocd/`, `vercel.json`, `apps/web/vercel.json`, `.gitmodules`, and `dev`.

## Workspace builds

The pnpm workspace contains nine package directories: the BFF and web applications, configuration, contracts, shared types, test utilities, and contract, E2E, and integration tests. The static visualizer has no package manifest, and the nested k6 project is outside the workspace patterns. Root build orchestration uses Turbo and package dependency ordering.

| Entry command                                 | Prerequisites                                                                                                 | Output or destination                                                                                   | Activation                                                                  | Usage                                                                                                                    |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `pnpm build`                                  | Node.js 20 or newer, pnpm 9, installed dependencies                                                           | BFF dist directory and Next.js production output; placeholder package build scripts print TODO messages | Invoked directly or by the CI build job                                     | Build all Turbo packages before packaging or running production builds.                                                  |
| `pnpm --filter @mini-commerce/bff build`      | Workspace dependencies installed; Prisma schema available                                                     | Generates Prisma client and compiles the Nest application into its dist directory                       | BFF package build script                                                    | Produce the server bundle used by the BFF runtime image.                                                                 |
| `pnpm --filter @mini-commerce/web build`      | Workspace dependencies installed; build-time public and proxy settings selected                               | Next.js production output; standalone output is enabled for its container image                         | Web package build script and Vercel configuration                           | Build the web interface and server-side proxy.                                                                           |
| `npm run build` from the k6 project directory | Node and npm dependencies installed; Punch submodule initialized because its shared report helper is imported | Bundled JavaScript in the k6 project's dist directory                                                   | Called from the k6 Docker image build, or directly for scenario development | Compile the nine HTTP and browser scenario entry points. The project cannot be selected by a root pnpm workspace filter. |

`@mini-commerce/shared-types`, `@mini-commerce/contracts`, and `@mini-commerce/test-utils` have placeholder build scripts. The configuration package has no build script. Contract package tests and typecheck scripts are placeholders; the test-utils and shared-types test and typecheck scripts are also placeholders. The BFF integration script is a placeholder. The performance package is managed with npm and is not included in the nine pnpm workspace directories.

## Container images

There are five Dockerfiles. The BFF and web images use the repository root as build context so workspace packages and lockfiles are available. The visualizer image serves static files. The two performance images compile scenario TypeScript in a Node builder stage and copy the results into k6 runtime images.

## Main Compose stack

The main Compose file defines nine services: PostgreSQL, BFF, web, OpenTelemetry collector, visualizer, Prisma Studio, Tempo, Prometheus, and Grafana. PostgreSQL, the BFF, and the collector have no profile and start with the core stack. Four optional profile groups enable the web app, visualizer, Prisma Studio, and observability services. The development overlay changes the BFF and web image stages and adds file watch rules; it also adds visualizer asset watch rules.

| Entry command or service      | Prerequisites                                                                               | Output or destination                                                                      | Activation                                                                                    | Usage                                                                                                |
| ----------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `./dev up`                    | Docker; Python 3.9 or newer; root environment file is optional because local defaults exist | PostgreSQL data in named volume; BFF on host port 3001; collector OTLP ports 4317 and 4318 | Starts the three unprofiled core services; the CLI prepares database migrations and seed data | Start the API and database stack. See [local development](../local-development.md) for the workflow. |
| `web` profile                 | Core stack available                                                                        | Web server on host port 3000                                                               | `./dev up web` or Compose profile `web`                                                       | Add the browser application.                                                                         |
| `visualizer` or `viz` profile | Core stack available                                                                        | Static visualizer on host port 3002                                                        | `./dev up viz` or `./dev up full`                                                             | Add the standalone visualizer.                                                                       |
| `admin` profile               | PostgreSQL healthy                                                                          | Prisma Studio on host port 5555                                                            | `./dev up admin` or `./dev up full`                                                           | Inspect database state directly.                                                                     |
| `obs` profile                 | Core collector running                                                                      | Tempo, Prometheus, and Grafana; host ports 3200, 9090, and 3030 by default                 | `./dev up obs` or `./dev up full`                                                             | View traces, metrics, and dashboards.                                                                |
| `./dev dev`                   | Docker Compose watch support; Python 3.9 or newer                                           | BFF and web use their dev stages; visualizer static files sync into Nginx                  | Development overlay with web and viz profiles                                                 | Run hot reload for application changes. See [local development](../local-development.md).            |

The three services in the development overlay are BFF, web, and visualizer. The overlay uses separate dev image tags for the BFF and web so these images do not collide with their runtime tags. It declares sync rules for BFF source, the web app directory, and visualizer public files. Web component source and web public files have no watch rule. Package manifests trigger BFF and web rebuilds; the visualizer image definition and entrypoint also trigger rebuilds.

## Performance Compose stack

The performance Compose project is separately named and has three services: `k6`, `k6-otel`, and `k6-browser`. Reports and datasets are bind-mounted from the host, so the compiled scenario scripts are baked into the images while generated data remains live between runs. The OTLP variant also joins the main stack's network and requires that network to exist first.

| Entry command or service | Prerequisites                                                                                 | Output or destination                                                                                        | Activation                                                                            | Usage                                                                                              |
| ------------------------ | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `./dev perf:<workflow>`  | Docker; Python 3.9 or newer; Punch submodule and its Python requirements; reachable app stack | Scenario summaries and logs in the performance reports directory; datasets in the performance data directory | Punch selects a workflow and invokes the matching performance Compose service         | Run a local performance workflow. See [performance orchestration](../performance/orchestrator.md). |
| `k6`                     | Performance image built; reachable BFF, normally through `host.docker.internal:3001`          | Host-mounted reports and datasets                                                                            | Default HTTP workflow runner                                                          | Execute HTTP scenarios.                                                                            |
| `k6-otel`                | Same as `k6`, plus the main Compose network and collector                                     | Same host-mounted outputs, with metrics sent to the collector                                                | Manual Compose invocation; none of the nine workflow definitions selects this service | Export k6 metrics to the local collector.                                                          |
| `k6-browser`             | Browser image built; reachable web app, normally through `host.docker.internal:3000`          | Same host-mounted reports and datasets                                                                       | Browser workflow selection                                                            | Execute UI scenarios using Chromium.                                                               |

## Kubernetes application deployment

The application base includes a namespace, PostgreSQL, collector, BFF, web, and visualizer. It generates the collector ConfigMap and a development PostgreSQL Secret. The BFF, web, and visualizer image references use `mini-commerce/bff:local`, `mini-commerce/bff-dev:local`, `mini-commerce/web:local`, and `mini-commerce/visualizer-3d:local`; the local operator workflow builds these images into minikube's Docker daemon, matching the manifest references. The BFF pod runs migrations and seeds through an init container before the API starts. Web proxy targets are baked into the web image at build time.

## Kubernetes performance platform

The performance base composes three overlays: Argo Workflows in namespace `argo`, SeaweedFS in namespace `aws-local`, and Punch runtime resources in namespace `punch`. The Punch overlay includes nine workflow templates, the generic runner base, six k6 option presets, an S3 artifact repository, and the locally built scenario images. The nine workflows are browser cart, browser purchase, HTTP authentication login, HTTP cart, HTTP hot-status, HTTP orders, HTTP order status, HTTP purchase, and registered-user purchase.

The local workflow builds both k6 images into minikube's registry addon using tags `localhost:5000/mini-commerce/k6:local` and `localhost:5000/mini-commerce/k6-browser:local`. Kustomize maps the generic scenario image names to those local tags. SeaweedFS provides the S3-compatible bucket `punch-artifacts`; workflow artifacts are written under per-workflow and pod keys. Dataset and run artifacts therefore persist in the object store rather than the local Compose report directory.

| ------------------------------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `./dev k8s:perf:up`                   | Minikube application cluster; registry addon; initialized Punch submodule                     | Argo Workflows controller and UI, SeaweedFS, Punch templates, image tags, option ConfigMap, artifact repository | Applies the performance Kustomize base                       | Install the local performance platform. See [Kubernetes performance runtime](../performance/k8s-runtime.md). |
| `./dev perf:<workflow> --runtime k8s` | Performance platform installed; application reachable in cluster; required datasets available | Workflow pod outputs in the `punch-artifacts` bucket in SeaweedFS                                               | Creates an Argo Workflow from the matching workflow template | Run one workflow on the cluster. See [Kubernetes performance runtime](../performance/k8s-runtime.md).        |
| `punch-artifacts` bucket              | SeaweedFS service and generated local credentials                                             | Reusable datasets and run artifacts under separate object prefixes                                              | Configured as the namespace's default artifact repository    | Store workflow inputs and outputs in the local cluster.                                                      |

## Argo CD applications and post-sync smoke

Two Argo CD Applications are defined. The mini-commerce Application points to the application overlay and targets the `mini-commerce` namespace. The punch-platform Application points to the performance platform. Both track `main` by default, leave pruning and self-healing disabled, and use server-side apply. The platform is applied first because the application's PostSync hook uses the HTTP purchase workflow template in the Punch namespace.

After all mini-commerce resources become healthy, the PostSync Workflow runs the one-iteration HTTP purchase smoke. A failed workflow marks the sync failed; the prior hook result remains inspectable until the next sync creates a replacement. `./dev argocd:up --revision <branch>` sets the revision for the local setup.

| Entry command or resource    | Prerequisites                                                                       | Output or destination                                         | Activation                                             | Usage                                                                                                     |
| ---------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| `./dev argocd:up`            | Minikube; application and performance platform; Git repository reachable by Argo CD | Argo CD install and two Applications in the cluster           | Installs Argo CD and applies the Application resources | Reconcile application and performance resources from Git. See [minikube runbook](../minikube-runbook.md). |
| `mini-commerce` Application  | Punch workflow template already installed                                           | Application resources in namespace `mini-commerce`            | Argo CD sync of the application overlay                | Reconcile the commerce application and run its PostSync smoke.                                            |
| `punch-platform` Application | Cluster access and upstream Argo Workflows manifests reachable                      | Argo Workflows, SeaweedFS, Punch templates and artifact store | Argo CD sync of the performance platform               | Reconcile cluster performance infrastructure.                                                             |
| PostSync smoke               | Healthy application resources and installed `http-purchase` template                | One-iteration Argo Workflow in namespace `punch`              | Runs automatically after a mini-commerce sync          | Verify the deployed API through the purchase workflow.                                                    |

## Vercel deployment

Vercel builds only the Next.js web application. The root configuration selects the web package build, emits `.next`, and sets demo mode with same-origin API behavior and no external visualizer link. The app-level configuration provides an equivalent web-only build when the project root is set to the web directory. Neither configuration deploys the BFF, database, visualizer service, or performance platform.

| Entry command or configuration | Prerequisites                                                      | Output or destination                   | Activation                                   | Usage                                                       |
| ------------------------------ | ------------------------------------------------------------------ | --------------------------------------- | -------------------------------------------- | ----------------------------------------------------------- |
| Root Vercel build              | Vercel project connected to the repository; pnpm install available | Next.js output for the web app, `.next` | Vercel project root is repository root       | Deploy the browser application in demo mode.                |
| App-level Vercel build         | Vercel project root set to the web application directory           | Next.js production output               | Vercel project root is the web app directory | Deploy the web app with the workspace root install command. |

## Submodule and artifact destinations

The Punch Git submodule is required for performance workflow orchestration and for both k6 image builds, which copy its shared report helper. A fresh checkout must initialize recursive submodules before those tasks. The local `./dev` entry point requires Python 3.9 or newer; performance commands additionally require Punch's Python requirements. The root Node workspace requires Node 20 or newer and pnpm 9.
